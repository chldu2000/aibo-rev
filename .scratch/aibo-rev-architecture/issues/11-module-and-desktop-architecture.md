## Question

在前序责任和不变量已明确后，采用什么模块划分、语言/桌面容器/存储方案与进程部署，能以较低维护成本覆盖完整版本？

区分逻辑模块与操作系统进程；围绕有实际变化的接口设计深模块，避免通用事件总线、插件平台或 UI 抽象仅搬运状态而增加合同数量。明确依赖方向、调用与订阅方式、生成/维护协议类型的责任及故障边界。

把 Zed 的结构化内容、统一会话状态、按类型渲染及动态配置作为参考，不继承其 GPUI 或已有 aibo 技术栈。使用维护成本、两个目标平台与实际工作负载评估候选，不以未验证的性能数字做决定。

范围依据：全部已选功能，尤其 F20 与 F25。

部署候选须满足 [生命周期决议](03-runtime-lifecycle.md#answer)，不能把单独 UI 故障或最后窗口关闭等同于整个应用的执行终止。

呈现职责遵循 [呈现接口决议](05-presentation-interface.md#answer)：默认包与外部包共用框架无关的数据/交互接口，共通状态可恢复。选型须证明明确失败能自动回退、无响应时有不依赖当前 UI 的手动恢复入口；逻辑模块不预设为独立进程。

[会话控制决议](07-session-control-and-delivery.md#answer)规定单一逻辑控制入口及输入、投递尝试、连接代际的区别。本票选择其实现与状态发布方式，不用长时间 prompt 等待阻塞取消/审批，也不把进程重启或通用消息总线当作去重与恢复保证。

[持续目标、子 Agent 与后台任务的职责](08-goals-and-background-work.md#answer)规定 Agent 原生推进、宿主协调控制并持有活动历史。本票落实共同活动状态、父子关联、目标/任务控制及按需只读补读接口；独立于视图和前台 prompt 接收事件，不增加宿主目标循环或按厂商分叉的 GUI。只读 ACP 扩展的范围/游标及完整性合同需在此具体化，不能用可触发执行的会话恢复替代。

[Agent 包、能力包与呈现包的生命周期](09-package-lifecycle.md#answer)规定三类贡献、可信代码模型及单版本生效。本票具体化本地交付格式、Agent 启动/探测/扩展映射入口、工具与用户上下文的无界面接口、MCP 接线与会话凭据、私有状态转换及呈现装载；生命周期由宿主统一协调，不以旧通用 Runtime 为前提，不以升级检查隐式恢复原生工作。一个包的单版本要求不预设每包单一进程或会话。

[持久数据、搜索与诊断的所有权](10-data-ownership-and-search.md#answer)规定权威写入、提交后发布、固定内容共享及保留责任。本票选择存储/索引方案与文件布局，落实输入和资源关系的原子性、索引追赶/重建、包与宿主格式演进、回收复核以及有界诊断；不把每类逻辑所有者拆成独立数据库或进程。明确批次、缓冲、有界读取及失效通知的接口，区分关键保存失败与索引/日志故障。长历史、并发流式输入和文件搜索的候选验证须记录实际工作负载及结果，不能从模拟呈现原型推定真实持久性和性能。

2026-11-04 补充：用户 Q71 允许分平台取得证据，可先形成带条件的候选与模块决定。[桌面候选在 Windows 的关键验证](17-windows-presentation-validation.md)承接最终架构收口前的 Windows 证据；若候选或接口因此变化，须回写本票。本轮实验使用的 Electron、React、Vue 均不自动成为产品选型。用户已撤销正式版本的特定设计系统/呈现风格要求。

## Comments

2026-11-10：用户要求整理剩余两项——共享无界面交互模块的位置与语言、公开呈现接口的传输与数据格式——开始认领。其余问题（进程部署、存储与索引、ACP 接入实现、工具面板装载）本轮不展开。

已核实的 MyGO 事实（[Bindings 文档](https://mygo.egoist.dev/docs/bindings)，2026-11-10）：`mygo.Bind` 暴露 Go 方法并生成 TypeScript 客户端，参数与返回值按 `encoding/json/v2` 序列化；`*mygo.Channel[T]` 按序流式推送，单次调用独占，页面积压超过约 1 MiB 时 `Send` 阻塞，页面关闭或离开时取消方法的 context；`mygo.NewEvent[T]` 的 `Emit`/`Broadcast` 可在无挂起调用时按窗口推送，无背压；`Protocol.Handle` 可用 `http.Handler` 提供页面资源。前序原型把共享交互状态放在宿主、两个框架经同一序列化接口（版本化快照 + 增量、缺口重同步）使用，只有焦点、选区、IME 等 DOM 辅助在页面侧。

决策树（第一轮只问前提已满足的问题）：

- 第一轮：Q72 共享交互状态的位置；Q73 公开接口与 MyGO 绑定的关系；Q74 持续更新的推送机制；Q75 消息编码；Q76 图片、附件与长正文的传输。
- 第二轮（依赖第一轮）：页面侧 SDK 的形态与分发；接口类型的权威来源与代码生成；订阅粒度与历史分段读取；增量更新的表达；草稿等本地编辑的同步时序。
- 第三轮：协议版本协商与兼容窗口；是否提供官方框架适配；工具面板是否复用同一协议。

第一轮问题，以下推荐均待用户回答：

- **Q72 — 共享交互状态放在哪里。** A：全部在 Go 宿主，页面只渲染。B：在页面内的框架无关 TypeScript 模块，由各呈现包引入。C（推荐）：权威与需恢复的状态（草稿已保存版本、附件/引用选择、审批作答、提交进度、错误）在 Go 宿主；页面侧只有薄客户端，负责订阅合并、正在编辑的本地值、焦点/选区/IME 等 DOM 辅助。推荐理由：呈现崩溃或换包后状态天然保留，所有框架共用一份实现；正在输入的文字留在页面，避免每次按键往返。
- **Q73 — 公开呈现接口与 MyGO 绑定的关系。** A：把宿主的 Go 服务方法直接 `Bind` 给呈现包，生成的 TS 客户端即公开接口。B（推荐）：自有版本化业务协议，只经少数通用绑定入口（如一次查询/命令调用、一次订阅）承载；MyGO 是传输层。推荐理由：外部呈现包依赖的是长期合同，不应随宿主内部方法重构而变化；也便于版本协商与旧实例校验。
- **Q74 — 持续更新的推送。** A（推荐）：每个订阅用一次 `Channel` 调用承载——按序、有背压、页面消失即取消，与呈现实例生命周期一致。B：用 `Event` 按窗口广播。C：两者混用。推荐 A；`Event` 不承载业务数据，必要时只用于窗口级通知。
- **Q75 — 消息编码。** A（推荐）：JSON（MyGO 原生），配合明确的 schema。B：二进制编码（MessagePack/Protobuf，经 base64 嵌入 JSON）。推荐 A；体积与解析成本先由分段读取和增量控制，有测量证据再考虑二进制。
- **Q76 — 图片、附件与长正文。** A（推荐）：经自定义协议 URL 读取（`Protocol.Handle`），URL 绑定呈现实例与读取范围，消息中只放引用与元数据；长正文分段读取。B：以 base64 嵌入 JSON 消息。推荐 A，避免大对象阻塞订阅流与 1 MiB 背压窗口。

2026-11-11：用户对第一轮全部采纳推荐：

- **Q72 = C。** 权威与需恢复的交互状态在 Go 宿主；页面侧只有框架无关的薄客户端（订阅合并、正在编辑的本地值、焦点/选区/IME）。
- **Q73 = B。** 公开呈现接口是自有版本化业务协议，经少数通用 MyGO 绑定入口承载；宿主内部 Go 方法不直接暴露给呈现包。
- **Q74 = A。** 每个订阅一次 `Channel` 调用；`Event` 不承载业务数据。
- **Q75 = A。** JSON 编码，配明确 schema；二进制编码须有测量证据才引入。
- **Q76 = A。** 图片、附件经自定义协议 URL 读取，URL 绑定呈现实例与读取范围；长正文分段读取。

第二轮问题，以下推荐均待用户回答：

- **Q77 — 页面侧客户端（SDK）的形态与分发。** A：发布 npm 包，由呈现包打包进自身。B：宿主经自定义协议按协议版本提供运行时客户端（如 `/_aibo/sdk/v1/client.js`），呈现包不打包。C（推荐）：B 为运行时唯一来源；另发布只含类型与开发用模拟宿主的 npm 包。推荐理由：运行时客户端与宿主协议实现同版本发布，不会出现包内旧客户端与宿主漂移；外部包作者仍有类型检查和脱离宿主的开发环境。客户端为纯 ES 模块，不依赖任何框架。
- **Q78 — 协议类型的权威来源。** A（推荐）：独立的 Go 协议包为权威（不得引用宿主内部类型），由它生成 JSON Schema 与 TypeScript 类型；CI 对比 schema 快照，非兼容变化须升协议版本。B：JSON Schema（或 TypeSpec）为权威，生成 Go 与 TS。C：Go 与 TS 各自手写，靠契约测试对齐。推荐理由：线上格式由 `encoding/json/v2` 实际序列化决定，以 Go 类型为源可避免 schema 与真实输出不一致；Go 侧从 JSON Schema 生成代码的工具较弱。
- **Q79 — 订阅粒度与历史读取。** A：每个呈现实例一个总订阅，推送全部工作台状态。B（推荐）：按主题订阅——一个工作台订阅（会话列表、通知、全局状态），每个打开的会话一个会话订阅（尾部窗口 + 状态条 + 待处理审批/问题）；更早的历史经分段查询按游标读取，不进入订阅。C：只按会话订阅，全局状态靠查询轮询。推荐理由：会话订阅与打开/关闭会话的生命周期一致，切走即取消，不为不可见会话付流量；历史分段读取与虚拟列表的向前加载对应。
- **Q80 — 增量更新的表达。** A：对快照的 JSON Patch（RFC 6902）。B：领域事件（如“审批已作答”），客户端自行推导状态。C（推荐）：按实体 ID 的整条记录替换/删除，外加流式正文专用的追加操作；每条增量带单调序号，客户端发现缺口即请求新快照。推荐理由：整条替换幂等、合并简单，外部包不必理解业务推导规则；追加操作控制流式输出的体积；与前序原型的“版本化快照 + 增量、缺口重同步”一致。
- **Q81 — 草稿等本地编辑的同步时序。** A（推荐）：输入停止约 400 ms 后保存到宿主；失焦、切换会话、发送前与页面隐藏时立即保存；IME 组合输入期间不保存；宿主以草稿版本号拒绝过期写入。B：只在失焦、切换和发送时保存。C：每次输入都同步。推荐理由：呈现崩溃时最多丢失不到半秒的输入，又不会每次按键往返；版本号防止两个窗口同时编辑同一草稿时旧值覆盖新值。

2026-11-11：用户对第二轮全部采纳推荐：

- **Q77 = C。** 运行时客户端由宿主经自定义协议按协议版本提供，是唯一运行时来源；另发布只含类型与开发用模拟宿主的 npm 包。客户端为纯 ES 模块，不依赖框架。
- **Q78 = A。** 独立 Go 协议包为类型权威（不得引用宿主内部类型），生成 JSON Schema 与 TypeScript 类型；CI 对比 schema 快照，非兼容变化须升协议版本。

第三轮问题，以下推荐均待用户回答：

- **Q82 — 协议版本协商与兼容窗口。** A：宿主只支持当前一个主版本，不匹配即失败。B（推荐）：宿主同时支持当前与上一个主版本；呈现包在清单中声明所需主版本与最低次版本，握手时确定；次版本只增加可选字段、新实体类型与新命令，客户端必须忽略未知字段与未知实体；无可用版本时按 05 号决议明确失败并自动回退默认呈现，提示原因。C：长期兼容所有历史版本。推荐理由：给外部包一个主版本周期的升级时间，又不让宿主背负无限兼容。
- **Q83 — 是否提供官方框架适配。** A（推荐）：只提供框架无关客户端，订阅接口采用 `subscribe`/`getSnapshot` 形状，可直接接入 React `useSyncExternalStore`、Svelte `createSubscriber`、Vue `shallowRef` 等；文档给出各框架几行示例；默认呈现的 Svelte 适配留在默认包内部，不是公开接口。B：发布 React/Vue/Svelte 官方适配包。推荐理由：适配层很薄，官方维护多套框架包会把框架版本升级变成宿主的维护负担，与降低维护成本的目标相悖。
- **Q84 — 工具面板是否复用同一协议。** A（推荐）：复用同一客户端、传输与编码（Channel 订阅、JSON、协议 URL），但面板会话按能力范围受限：只能访问所属能力包的数据、当前工作区/会话的有限只读信息，以及“向输入框添加附件或引用”等明确命令；不能读取未发送草稿，也不能代替用户发送（[界面方案 §8](../../../docs/design/ui-interaction.md)）。B：工具面板使用独立协议。推荐理由：一套协议、一套客户端，权限由握手时的范围决定。面板的装载方式（同文档、独立文档或独立 WebView）仍是本票单独的问题，不在本轮决定。

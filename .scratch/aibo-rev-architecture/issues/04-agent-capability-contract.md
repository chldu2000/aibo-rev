## Question

完整版本对 Codex、Claude Code 和新增 ACP Agent 分别承诺哪些功能？标准和协商后的扩展如何进入统一会话接口，缺失或失效能力怎样显示及拒绝操作？

确定标准/草案/厂商扩展的接纳规则、版本与能力声明、扩展语义转换的归属，以及需要自维护 ACP 适配器时的责任。所有 Agent 使用同一 ACP 路径，没有内置/外部分支；“允许扩展”不等于每个 Agent 都已有扩展。

确认必需功能是平台级能力还是要求每个目标 Agent 全部具备；不要静默下调 Checklist。

范围依据：F02、F04.9、F05、F08–F09、F11–F12。

## Comments

2026-11-01：用户询问本票需要确认的问题，开始认领。依据已完成的 [ACP 能力覆盖研究](../../../docs/research/acp-required-capabilities.md)讨论产品承诺；不重新打开“全 ACP、允许扩展、不区分内置/外部”的既定约束。

首轮问题（提问时推荐尚未经用户接受）：

- Q12：Checklist 的 Agent 相关能力是否要求 Codex 和 Claude Code 全部对等？推荐按平台承诺逐项交付，每个所选功能必须至少有可验收的真实路径；不同 Agent 可以明确不支持部分能力，不能仅显示空入口就算完成。
- Q13：愿意承担多少 ACP 适配器维护？推荐优先使用上游，允许必要且范围明确的补丁/扩展，避免默认承担完整长期分叉；支持自有 ACP 适配器仍不等于宿主增加原生协议旁路。
- Q14：经过版本约束与验证的草案/第三方扩展能否作为正式功能？推荐允许逐项采用，明确其合同及维护责任；未验证扩展不自动变为功能。
- Q15：兼容承诺绑定验证过的版本范围，还是跟随系统任意版本？推荐对验证过的组合提供保证，对其他版本如实标记未验证并继续按能力协商；安装与升级机制留在包生命周期票。

这些回答之后再确定每个 Agent 的最低接入基线与缺失能力处理；本票不替 [持续目标、子 Agent 与后台任务的职责](08-goals-and-background-work.md)决定宿主是否实现特定编排，也不替 [业务历史与跨 Agent 引用的权威来源](06-history-reference-authority.md)决定原始 transcript 的范围。

2026-11-03，记录用户首轮答复：Q12–Q15 均按推荐。Q15 的最终选项明确为“允许兼容但未验证的 Agent/适配器组合接入，标记未验证；正式支持限于经过测试的组合”，不是只允许安装验证过的版本。

第二轮问题及用户答复：

- Q17：Agent 不支持某项核心功能时，保留禁用入口并说明原因。用户选择推荐 A。
- Q18：标准 ACP 由共享模块处理，厂商扩展在独立的扩展处理模块解释和转换，可随 Agent 包交付；运行核心和 GUI 使用共同的会话与能力模型，不预设增加进程或另一套通信协议。用户选择推荐 A。

## Answer

2026-11-03，根据用户 Q12–Q18 的选择，采用**统一 ACP 基础接入、按能力启用功能、按已验证组合提供正式支持**的承诺。全部 Agent 仍走同一 ACP 路径，不按内置/外部或验证程度拆成不同执行体系。

| 决策 | 已确认承诺 |
| --- | --- |
| 平台功能与 Agent 差异（Q12） | Checklist 所选功能逐项交付，每项至少有真实、可验收的端到端路径；不同 Agent 可以缺少部分能力。Codex、Claude Code 和通用 ACP 接入仍在范围内，不要求两家高级能力完全对等，也不能用空入口代替交付 |
| 适配器维护范围（Q13） | 优先使用上游，允许必要且范围明确的补丁或扩展；不默认承担完整适配器的长期分叉。自有适配器对宿主仍暴露 ACP |
| 草案与厂商扩展（Q14） | 可以成为正式功能，但须明确合同、版本约束、能力协商、验证方式和兼容维护责任；声明支持或存在源码路径本身不足以完成验收 |
| 未验证组合（Q15） | 兼容的 Agent/适配器组合允许接入，明确标记未验证；正式支持只覆盖经过测试的组合。未验证与协议不兼容、不支持某项能力分别表达 |
| 最低接入门槛（Q16） | 基础会话与文本流、取消请求、正确处理该 Agent 所需的权限交互，以及允许宿主保存已观察历史、发送其他会话的文本引用。该门槛适用于所有 Agent |
| 缺失能力的呈现（Q17） | 核心功能保留禁用入口并说明原因，使用户可以了解 Agent 差异；不能将不可执行的操作呈现为已经成功 |
| 扩展解释的归属（Q18） | 共享模块处理标准 ACP；独立扩展处理模块解释和转换厂商扩展，可随 Agent 包交付。运行核心和 GUI 共用会话与能力语义，不各自解析厂商字段 |

**最低接入门槛不缩减完整版本。** 原生恢复、图片、MCP 全文读取、插话、持续目标等不要求每个 Agent 都具备，仍按 Checklist 逐项提供可验收路径。若某项尚无可用路径，应保留为交付缺口，不能以“可选能力”将其视为已完成。目标、子 Agent 和后台任务要按具体动作判断，不能用一个笼统的“支持高级功能”标记覆盖语义差异。

**对后续架构的约束：**

- 能力模型应分别表达支持情况、当前可用性与操作授权；验证程度另行记录。例如，未验证的组合不必禁用其全部功能，已验证且支持的能力也不意味着此刻已授权执行。
- GUI 使用共同模型展示可用操作与禁用原因；执行入口也须依据实际能力拒绝不支持的操作。能力变化、失效及迟到结果的处理由会话控制决议细化，不能只靠按钮状态约束执行。
- 扩展处理模块集中承担版本差异、能力声明和语义转换，避免在运行核心与不同呈现包重复厂商分支。这里确定的是模块职责，不要求新进程、额外通信协议或照搬旧插件接口。
- 取消请求属于基础能力；请求已发送不等于任务已停止。停止确认与结果未知继续遵循 [生命周期决议](03-runtime-lifecycle.md#answer)。
- 宿主保存已观察历史并发送文本引用，不等于获得原始 transcript；原始格式、完整性、补读与引用版本仍由历史决议确定。MCP 全文读取不是所有 Agent 的最低接入要求，也仍是平台必需功能。

## Question

依据已讨论的呈现接口和运行/投递不变量，是否能用两个不同框架实现同一组关键交互，在不改内核合同的情况下完成完整视图替换与外部呈现包加载，并在约定故障后恢复？

使用可丢弃的模拟内核和最小桌面候选验证会话切换、流式内容、草稿/引用、审批、失联重挂载与默认回退。需让用户实际评价结果，不能以 agent 自评代替 HITL。本票调用 prototype 技能，不开发产品实现。

候选接入形式从前序讨论收敛；只做足以回答选型疑问的原型，不同时搭建所有框架和容器。记录核心或合同被迫修改的位置、未满足的不变量和资源释放结果。

参照 [框架中立呈现研究](../../../docs/research/framework-neutral-presentation.md)的六项场景，区分浏览器可验证项与必须在 macOS/Windows 原生环境验证的项。无法运行的系统标为待验证，不将静态证据或单平台结果外推。

原型结论供 [模块接口、技术栈与桌面部署形态](11-module-and-desktop-architecture.md)采用、修正或否定候选；若暴露新问题，再建对应决策票。

## Answer

2026-11-04，结合已取得的 macOS 实验结果与用户明确认可，本原型**基本通过**，本票 resolved。结论是：共同业务与无界面交互模型可以支撑两个独立框架的完整关键流程，呈现实例可整体替换，并能在本次验证条件下恢复；这一结果足以作为后续正式设计的依据。

实验资产固定于 `prototype/presentation-conformance` 分支、提交 `83ac7e8e6b4f0020aff88d74e76a6e8db90d1ba1`，入口为 `prototypes/presentation/README.md`，观察记录为 `prototypes/presentation/OBSERVATIONS.md`。当前工作树可直接阅读[运行说明](../../../../aibo-rev-presentation-prototype/prototypes/presentation/README.md)和[macOS 观察记录](../../../../aibo-rev-presentation-prototype/prototypes/presentation/OBSERVATIONS.md)；后者保存的是该次实验时点的事实与限制，最新用户接受结论以本票为准。

已取得的关键证据包括：

- React 与 Vue 的独立构建、完整关键视图替换，草稿、固定引用、审批身份、历史分段位置和输入选区保持一致。
- 旧呈现实例操作被拒绝，同一命令没有重复入队；更新缺口触发快照重同步。
- 真实渲染进程崩溃后的默认回退，以及页面死循环时宿主继续运行、独立恢复处理仍可重建呈现。
- 未知投递在替换及故障恢复后未自动重发；模拟保存失败的暂停状态保留，恢复存储未自动恢复工作。
- 日常及压力样本下的短期运行、资源释放和成本测量，具体口径与限制保存在观察记录。

本次接受不将原型使用的 Electron、React、Vue、实验 manifest、窗口组织或控件布局定为正式方案。用户将后续单独设计正式版本的技术栈、用户界面与交互；暂不指定设计系统或呈现风格。现有业务责任与行为约束作为设计输入，未来若明确调整则回写对应决议。

用户接受原型，不补写尚未取得的事实：Windows、逐项真实 IME/菜单/剪贴板/拖放/选择器、长期资源表现，以及真实 ACP/持久化仍不因此标为已验收。它们随正式方案进入对应验证；[桌面候选在 Windows 的关键验证](17-windows-presentation-validation.md)保留后续责任，不要求继续以当前 Electron 原型作为唯一候选。

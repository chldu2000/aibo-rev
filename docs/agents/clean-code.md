# Clean Code 规范

适用于 aibo-rev 的全部产品代码与测试（Go、MyGO 原生 UI）。原型不受本规范约束，但从原型借来的代码进入产品时必须符合本规范。

目标只有一个：**降低维护成本**（[ADR 0002](../adr/0002-aibo-refactor-direction.md)）。一处修改只改一处，读一个模块就能理解它的行为，测试只走模块的接口。下面每条规则都服务于这个目标；不确定时，选让下一个读者更省力的写法。

规则与 ADR 或界面要求冲突时，以 ADR 和要求文档为准，并报告冲突。

## 1. 命名

- 用 [CONTEXT.md](../../CONTEXT.md) 的术语命名类型、函数和测试：`SessionEntry`、`SessionBinding`、`QueuedInput`、`DeliveryAttempt`、`DeliveryEvidence`、`ReferenceHistoryVersion`、`ReferenceReadGrant`、`ProtectedData`。术语表标为“避免”的说法，在代码里同样不用。缺少术语时先补到 CONTEXT.md，再写代码。
- 名字说明它是什么、做什么，而不是怎么实现：`pendingApprovals` 而不是 `approvalMap`。
- 作用域越大，名字越完整；循环变量、接收者可以短（`s *Session`）。
- 包名用职责命名，短、小写、单数：`acp`、`store`、`delivery`。不建 `util`、`common`、`helpers`、`models`、`types` 这类按“种类”归堆的包。
- 不重复包名：`delivery.Attempt`，而不是 `delivery.DeliveryAttempt`。
- 布尔值读起来像判断：`trusted`、`hasPendingApproval`、`canSteer`。
- 状态用具名常量或枚举类型，不用裸字符串或数字。“结果未知”是一个独立状态，不与失败合并。

## 2. 模块与依赖

- 设计**深模块**：小接口、多行为。新建模块前做删除测试：删掉它以后复杂度是消失（它只是转手，不该存在）还是散落到各调用方（它有价值）。
- 依赖方向固定（[ADR 0006](../adr/0006-native-ui.md)）：

  | 模块 | 可以依赖 | 不得依赖 |
  | --- | --- | --- |
  | 运行核心（会话、ACP、投递、存储） | 标准库、协议类型 | MyGO 的任何包 |
  | 交互层 | 运行核心 | MyGO `ui` |
  | 界面包 | 交互层、MyGO `ui` | 运行核心、ACP 连接层、存储 |
  | 桌面宿主 | MyGO、交互层 | — |

  工具面板协议的类型放在独立的 Go 协议包中，不引用宿主内部类型（ADR 0004 §3）。
- 接口在**使用方**定义，只含使用方需要的方法。只有存在两个实现时（包括测试替身替换外部进程或文件系统）才引入接口；只有一个实现就直接用具体类型。
- 不引入通用事件总线、服务定位器或依赖注入框架。依赖通过构造函数显式传入。
- 不为“以后可能需要”预留扩展点、配置项或参数。需要时再加。
- 包内未导出是默认；只导出调用方确实要用的标识符。

## 3. 函数

- 一个函数只做一件事，内容停留在同一抽象层级。读者需要滚屏才能看完的函数，通常应该拆分。
- 先处理错误和边界，提前返回；主路径不缩进。
- 会阻塞、做 I/O 或可取消的函数，第一个参数是 `ctx context.Context`。
- 不用布尔参数切换行为。拆成两个具名函数，或用具名选项类型。
- 参数超过三四个时，考虑它们是否本该属于同一个结构体。
- 没有副作用的计算写成纯函数，方便测试；副作用集中在少数边界上。

## 4. 状态与并发

这一节是正确性要求，不只是风格。

- **每份可变状态有唯一的所有者。** 其他 goroutine 通过消息或所有者的方法访问，而不是共享加锁。
  - 每个 Aibo 会话一个控制 goroutine，串行处理用户命令与 ACP 事件（ADR 0005 §3）。
  - 数据库只有一个写入 goroutine；读取可以并发（ADR 0005 §2）。
  - 界面读取的状态只在 MyGO 界面线程上修改；其他 goroutine 的变化经 `Window.Update` 投递（ADR 0006）。
- **先落库，再对外动作或发布。** 投递尝试先写入再调用 `session/prompt`；状态变更先写库再通知界面；大内容先写临时文件、落盘、改名，再在事务中登记。
- **如实表示状态。** 请求已发出不等于已生效。代码中不把“已发送停止”“已投递”等写成成功，直到收到证据；结果未知时不自动重发（决议 07、UI-GEN-02）。
- 每个 `go` 语句都有明确的结束条件（`ctx` 取消、通道关闭）以及由谁等待它结束。不留无人管理的 goroutine。
- 界面线程上不做阻塞工作：高亮、搜索、大文本处理放到其他 goroutine，结果经 `Window.Update` 送回（UI-STREAM-05）。
- 不用 `time.Sleep` 做同步。等待用通道、`sync.WaitGroup` 或 `ctx`。
- 时间、随机数、ID 生成通过参数注入，测试中可替换。

## 5. 错误处理

- 错误要么处理，要么带上下文返回：`fmt.Errorf("投递尝试 %s 写入失败: %w", id, err)`。不要静默丢弃；确实可以忽略时，写一行注释说明原因。
- 调用方需要据以做决定的错误，定义为哨兵错误或错误类型，用 `errors.Is` / `errors.As` 判断，不比较错误字符串。
- 同一个错误只在一处记录日志：要么记录并处理，要么返回，不两者都做。
- `panic` 只用于程序员错误（不可能出现的状态）。可预期的失败返回错误。
- panic 边界（ADR 0006 后果、`workbench-shell` 的结论）：
  - 视图构建在区域外层元素的 `Children` 闭包内 recover，只让该区域显示故障说明与“重试”；边界不放在切换主题作用域的元素内部。
  - 事件回调和每个长期运行的 goroutine 在顶层 recover，写诊断日志并把故障转成可见状态，而不是让应用退出。
- 关键保存失败暂停推进并说明原因（决议 10、UI-LIFE-03），不吞掉、不重试成假成功。

## 6. 数据与协议

- JSON 使用 `encoding/json/v2`，类型以 Go 为源生成 schema（ADR 0004 §3）。
- ACP 消息中未识别的字段保留原文，不丢弃（ADR 0005 §3）。
- 大对象（图片、附件、超过阈值的工具输出）走内容寻址文件与协议 URL，不 base64 嵌入消息。
- 数据库结构变更写成有序迁移，迁移在副本上验证；不手改已发布的迁移。
- 区分数据职责（CONTEXT“数据职责”）：业务历史、恢复状态、投递证据、审计事实、过程明细、派生索引分别建模，各有保留规则。不把过程明细当业务历史保存，也不把受保护数据当诊断明细清理。

## 7. 界面代码

界面的硬性要求见 [ui-requirements.md](../design/ui-requirements.md)，本节只补充写法。

- 视图是视图模型的函数：从交互层取只读视图模型，渲染；用户操作调用交互层的命令。视图中不做业务推导。
- 颜色、字号、间距、圆角、尺寸只来自生成的令牌，不写字面值（`static` 检查会拦截）。
- 组件外观集中在 Aibo 自己的组件封装里（方案 A“玻璃胶囊”，参考 `workbench-shell/kit.go`）。页面代码使用封装，不在各处重新拼样式。
- 无障碍角色与名称遵循要求文档 §11.1 的契约；测试与读屏都依赖它们。
- 界面文字全部走本地化资源（UI-I18N-01），不在视图代码中硬写中文或英文。
- 夹具只存在于测试代码中，不进入发布构建（UI-GEN-04）。

## 8. 注释与文档

- 导出的标识符有文档注释，以名字开头，说明它是什么、调用方需要知道的约束（顺序、并发安全、错误含义）。
- 注释写“为什么”，代码本身说明“做什么”。规则来自 ADR、决议或要求条款时，注明出处，例如 `// 先落库再发送（ADR 0005 §3，决议 07）`。
- 不留注释掉的代码；Git 历史会保存它。
- `TODO` 必须附票号：`// TODO(17): Windows 上核实 Job Object 清理`。
- 实现中做出了文档里没有的决定，回写到对应 ADR、决议或要求文档，而不是只留在代码注释里。

## 9. 测试

- 测试通过模块的接口进行。需要绕过接口才能测试时，通常说明模块形状不对。
- 界面测试用 MyGO `ui.Tester`，按无障碍角色与名称定位元素；`uitest` 条款的用例放在 `tools/ui-checks/acceptance`，`ID` 为条款编号。
- 外部进程（Agent、能力包）在接口处用测试替身替代；数据库测试使用真实 SQLite（临时目录），不模拟 SQL。
- 测试确定且快：注入时钟，不依赖真实时间、网络、用户目录或执行顺序。不用 `time.Sleep` 等待。
- 多组输入输出用表驱动测试；测试名描述行为：`TestUnknownDeliveryIsNotResent`。
- 修复缺陷先写一个复现它的失败测试。

## 10. 依赖与工具

- 优先使用标准库与 MyGO 已提供的能力。新增第三方依赖要在变更说明中写明理由；不得引入需要 cgo 的依赖（ADR 0006 约束 2）。不使用社区 Go ACP SDK（ADR 0005 §3）。
- 提交前：`gofmt`（或 `goimports`）、`go vet ./...`、`CGO_ENABLED=0 go test ./...` 通过；涉及界面时再加 `go -C tools/ui-checks run . all`。
- 生成的文件（令牌等）只经生成器修改，文件头注明来源。

## 11. 变更

- 一次变更只做一件事；重构与行为修改分开提交。
- 删除死代码、未用的参数和过时的分支，不保留“以防万一”。
- 不为旧 Aibo 的格式或合同写兼容层（架构地图 Q4、D08）。
- 离开时代码比来时更干净，但顺手的整理只限于正在修改的模块。
